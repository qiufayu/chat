# 即时通讯平台开发技术选型说明

文档版本：1.0  
确定日期：2026年10月18日  
适用范围：第一版项目开发与技术验收  
依据文件：本目录中的《产品需求说明书》  
已确认的用户要求：使用 JDK 17，使用 RabbitMQ。

本文说明选择哪些技术、分别解决什么问题，以及它们如何支持业务正确性。必要技术用语在使用处解释，不包含代码示例、代码引用或安装命令。

## 一、选型结论

后端采用 JDK 17、Spring Boot 3.5.x、Spring Cloud 2025.0.x 和 Spring Cloud Alibaba 2025.0.x；实时通信采用 Netty 与 WebSocket；业务数据使用 MySQL 8.4；在线路由和临时数据使用 Redis；消息分发使用 RabbitMQ；前端使用 Vue 3 与 TypeScript。

JDK 是编译和运行 Java 程序所需的开发工具。本项目的开发、编译、测试和运行均以 JDK 17 为基础，不使用必须依赖更高版本才能运行的功能。

本项目的技术重点依次为：

1. 多人同时操作时，消息、群成员、权限和阅读状态仍然正确。
2. 网络中断、重复提交和服务重启后，可以确认原操作结果并恢复使用。
3. 在正确性成立的前提下，验证持续收发、群聊分发和多设备使用的处理能力。

消息队列用于可靠地传递待处理事件；聊天记录及其业务顺序以 MySQL 中的记录为准。不能因为采用某种消息队列，就省略消息去重、权限检查和断线补拉。

## 三、版本兼容与统一管理

### 3.1 后端版本组合

确定采用以下兼容系列：JDK 17、Spring Boot 3.5.x、Spring Cloud 2025.0.x、Spring Cloud Alibaba 2025.0.x。

其中的 x 表示同一版本系列中的修订版本。Spring Cloud Alibaba 官方说明中，2025.0.x 系列对应 Spring Boot 3.5.x、Spring Cloud 2025.0.x，最低支持 JDK 17，因此这组版本可以采用本项目确定的 JDK 17。

Netty、Spring Security、Spring AMQP、数据库连接工具等，优先采用 Spring Boot 和 Spring Cloud 提供的统一兼容清单。统一兼容清单是框架已经协调过的一组依赖版本，不单独把其中某个组件随意换成最新版本。

MyBatis-Plus 应使用适配 Spring Boot 3 的接入方式。Flyway 应包含适配 MySQL 的支持。所用阿里云文件访问工具也必须在 JDK 17 下验证。

### 3.2 精确版本的固定规则

1. 本文确定技术和版本系列，不把未经实际启动验证的补丁组合宣称为已经可用。
2. 初始化项目时，为每个独立组件选择该系列已经正式发布、通过兼容检查的精确版本，并记录在项目的统一版本清单中。
3. 前端保留依赖锁定文件，即记录实际安装版本的文件；后端统一管理依赖版本。不同开发者使用相同清单。
4. 正式环境不得使用会随时间自动变化的版本标记，也不得使用尚未正式发布的试验版本。
5. 升级前重新验证消息重复处理、消息顺序、权限、群人数和恢复能力，不仅检查程序能否启动。

## 四、程序职责与数据边界

### 4.1 第一版的三个主要服务

| 服务 | 负责的内容 | 数据边界 |
| --- | --- | --- |
| 入口服务 | 普通请求转发、入口流量限制、初步身份检查 | 不直接修改聊天、群成员和阅读状态 |
| 连接服务 | 实时连接、心跳、连接身份、设备路由和设备推送 | 不直接写入核心业务表，不自行决定用户是否仍有发言权限 |
| 核心业务服务 | 账号、好友、群组、会话、消息、阅读状态、文件授权、举报和后续分发安排 | 统一拥有核心业务数据，处理必须一起完成的操作 |

核心业务服务内部按业务划分模块。模块是同一程序内部的职责分区，不等于必须拆成多个独立服务。

第一版的消息发送、好友状态检查、群成员检查和群状态变更保留在同一个核心业务服务内。核心业务服务可运行多个实例，即同时运行多份相同程序，它们遵循相同的数据约束和事务规则。

不得先由一个独立服务检查允许发言，再不加协调地让另一个服务保存消息。这样会留下检查通过后用户已被踢出群、但消息仍被接受的空隙。

### 4.2 数据保存原则

1. MySQL 保存用户、登录设备及其撤销状态、好友关系、群组、群成员历史、会话顺序、消息、阅读进度、操作结果和待分发事件。
2. Redis 保存连接位置、短期计数和可重建的副本；登录相关副本失效时，应回到持久记录核对，不能自动恢复已经撤销的登录。
3. RabbitMQ 保存待处理事件，不承担历史聊天查询、180天聊天保存和用户离线记录的唯一来源职责。
4. OSS 保存附件内容，MySQL 保存文件归属、状态及其与消息的对应关系。仅知道文件位置不代表有访问权。
5. 连接服务之间的路由变化，不得改变消息是否已经保存，也不得改变原消息顺序。

## 五、RabbitMQ 的使用方案

### 5.1 选择 RabbitMQ 的原因

本项目需要异步分发、短时流量缓冲、失败重试和多种后续处理。异步是指主操作完成后，由其他处理步骤继续执行，不要求用户等待全部步骤完成。

RabbitMQ 能满足这些需要，并具备发送结果确认、消费结果确认以及多副本队列等机制。消息顺序和数据正确性仍由业务规则保障，不依赖队列天然实现全部要求。

### 5.2 消息与事件的区别

聊天消息是用户发送的内容，保存在 MySQL 中。事件是通知后续程序开展工作的记录，例如一条聊天消息已经保存、需要安排分发。

同一条聊天消息可能引起分发、会话摘要更新或业务通知等不同工作。不同用途应分别安排处理，不让某个非必要步骤失败阻塞全部聊天。

### 5.3 从保存到分发的完整过程

1. 核心业务服务确认登录、账号、好友或群成员资格，并核对这是否为已经处理过的发送。
2. 在同一个数据库事务中，保存操作结果、正常聊天消息和待分发事件。事务表示一组数据变更一起成功，发生失败时一起撤销。
3. 数据库确认提交完成后，才能向发送者表示消息已保存；数据库结果不确定时，不得猜测成功或失败，应允许核对原操作。
4. 后台任务读取待分发事件，发送给 RabbitMQ。待分发事件与消息一起保存的做法称为本地消息表，也常称 Outbox。
5. 发送程序等待 RabbitMQ 的发布确认，即队列系统确认接收事件的结果；同时检查事件是否确实找到目标队列，不能把无人接收的事件当作成功。
6. 确认成功后更新事件发送状态。若确认丢失或更新状态前发生重启，允许再次发送同一事件。
7. 消费程序按事件编号识别重复处理，并持久保存分发安排及对应进度；持久保存是指程序重启后仍能找到记录。
8. 分发安排保存成功后，才给 RabbitMQ 消费确认，即表示此阶段工作已完成。若工作尚未保存，不得提前确认。
9. 根据 Redis 中的设备位置，将消息交给对应连接服务。连接服务收到推送任务，不等于接收者已收到消息。
10. 接收设备明确确认收到后，才记录单聊已送达；用户实际阅读后，再推进已读位置。暂时离线、接收失败或路由变化时，按规则重试或由重连补拉恢复。

这个过程采用至少一次处理，即为了避免遗漏，允许事件被重复传递。重复事件不应产生重复业务结果，这种性质称为幂等。不能把发布确认、消费确认或连接写入成功直接解释为用户已读。

### 5.4 队列可靠性与环境区别

1. 关键业务事件采用持久化队列和持久化消息，即正常重启后应保留未完成事件。
2. 关键队列采用仲裁队列。仲裁队列通过多个节点保存副本，并依赖多数副本可用来继续正常工作。
3. 本地开发允许单节点 RabbitMQ，但只能证明基本功能，不能据此声称具备机器故障下的多副本保护。
4. 验证单台机器故障恢复时，使用至少3个 RabbitMQ 节点，并放在不同机器上。同一台电脑中的多个程序不能证明整台电脑损坏后的恢复能力。
5. 队列不可用时，已经提交的本地消息表记录应保留待发送。未完成事项持续增加时，应告警并按需求限制新流量，而不是删除事件。
6. 本地消息表已发送记录和消费记录的清理应有明确期限，能够覆盖允许的重试和人工重放范围；不能先清理去重依据，再重新执行有副作用的旧事件。

### 5.5 重试、异常队列与人工恢复

1. 短暂故障按逐步增加的等待间隔重新处理，不进行没有间隔的无限循环。
2. 超过自动重试次数后，将事件移入异常处理范围，保留失败原因、次数和原事件编号。
3. 死信队列是保存无法继续正常处理事件的队列。使用前应明确何时进入、由谁处理，以及如何重新执行。
4. 对关键队列之间的失败转移，应配置并验证可靠的转移方式；仅设置死信目标，不等于已经证明事件不会遗漏。
5. 人工重新执行仍使用原事件编号和业务约束，不能绕过去重、权限或撤回规则。
6. 已经完成业务工作但确认丢失时，再次处理只能确认原结果，不能重复增加未读或反复发送业务通知。

### 5.6 顺序与跨连接节点投递

1. 多个消费者同时处理、失败重试和网络变化都可能改变事件到达顺序。因此，聊天显示以数据库的会话序号为准。
2. 需要按顺序执行的后续业务，按会话分配到固定处理范围，并核对已处理位置；不能仅凭队列到达顺序认定业务顺序。
3. 单个活动消费者是同一队列同时只由一个消费者执行工作的方式，可用于需要限制处理交错的场景，但不能代替业务去重和序号检查。
4. 连接服务不能共用一个普通任务队列，并假设每条事件会自动送到用户所在的那台连接服务。消费到事件的分发程序必须查询实际路由，再明确交给目标服务。
5. 第一版使用经过身份校验的内部 HTTP 调用执行跨连接节点推送。调用等待过久时，应保留不确定结果并按原消息身份核对，不另造一条聊天消息。
6. 单个用户暂时无法接收，不应导致整个群的分发任务反复从头执行。应按设备或可恢复的小批次记录处理进度。

## 六、并发数据正确性方案

并发是指多个操作在相近时间内交错执行。本章说明由哪些机制支持《产品需求说明书》中的正确性要求，不把组件名称当作正确性的证明。

### 6.1 基础机制说明

| 机制 | 含义 | 本项目用途 |
| --- | --- | --- |
| 唯一约束 | 数据库禁止保存两份具有相同业务身份的记录 | 消息重试去重、成员身份去重、好友关系去重 |
| 数据库事务 | 多项变更共同成功或共同撤销 | 消息与待分发事件一起保存，群主转让完整完成 |
| 行锁 | 在事务完成前，让其他冲突操作等待同一条控制记录 | 群名额、会话序号、群权限和账号状态的竞争处理 |
| 条件更新 | 只有记录满足指定条件，才允许变更 | 阅读位置向前推进、名额未满才增加成员 |
| 版本校验 | 变更时确认资料仍是用户先前看到的版本 | 避免旧页面无提示覆盖新的群资料 |
| 原子操作 | 一组检查与变更不能被其他操作从中间插入 | 仅在仍是旧连接时移除对应 Redis 路由 |
| 数据核对 | 根据权威记录检查并修复派生状态 | 恢复会话摘要、未读显示和分发进度 |

MySQL 第一版采用读已提交的事务隔离级别，即事务读取其他事务已经提交的数据。隔离级别是数据库限制多个事务互相影响的方式，但它本身不能消除所有竞争，仍需正确的锁、约束和更新条件。

所有可能互相冲突的操作应遵循统一的加锁顺序，涉及多名用户时按稳定的用户顺序处理。发生死锁，即两个事务互相等待对方释放资源时，应撤销其中一个并以原操作身份进行有限重试，不能生成新业务操作。

### 6.2 业务要求与实现原则

| 业务场景 | 实现原则 | 验收结果 |
| --- | --- | --- |
| 同一次发送重复提交 | 发送编号与用户共同构成唯一业务身份；保存并复用原结果 | 无论重试次数多少，只产生一条消息 |
| 重试内容被意外修改 | 校对原发送内容及关键属性；不允许相同发送编号代表两份不同内容 | 明确拒绝冲突，不覆盖原消息 |
| 已拒绝发送在权限恢复后又重试 | 对已识别且明确拒绝的业务发送保存结果；恢复权限后必须主动创建新发送 | 原失败操作不会自动变成成功 |
| 多人同时发送群消息 | 锁定会话控制记录，在事务内分配顺序并保存消息 | 同一会话位置不重复，全部用户最终顺序一致 |
| 群发言与禁言、踢人或解散交错 | 这些操作协调同一群控制记录，在事务内读取当前有效权限 | 可以按明确生效先后解释每条接受或拒绝结果 |
| 删除好友或拉黑与单聊发送交错 | 发言和关系变更协调同一关系控制记录 | 关系限制生效后不再接受新发送 |
| 群人数接近500人 | 锁定群控制记录，名额校验、成员增加和申请结果一起提交 | 不重复占位，不超出500人 |
| 管理员最多5人 | 在受保护的群变更中核对身份和管理员数量 | 不突破上限，不能出现重复管理员身份 |
| 群主转让及每人最多拥有20个群 | 协调群控制记录及相关用户的群主数量记录 | 每群始终一名群主，接任者不超限 |
| 多设备更新已读 | 先确认阅读位置合法，再只接受更靠后的有效位置 | 已读不倒退，也不能跳到无权查看的位置 |
| 未读数量处理 | 根据可见、未撤回、非本人发送且在阅读位置之后的消息核对 | 不用简单相减推断人数变化后的未读，不因重复事件多计 |
| 新旧连接交错 | 路由包含设备、连接和连接服务实例的身份；比较后再更新或删除 | 旧连接不能取消新连接或其他设备 |
| 账号停用、设备退出与发送交错 | 核心事务核对持久化登录与账号状态，并与撤销操作协调 | 旧请求不能恢复失效登录，停用后不能继续新发言 |
| 原消息晚于撤回结果到达 | 保存并比较消息的更新版本；撤回是后续不可逆状态 | 原文不能因晚到数据重新出现 |
| 旧摘要晚于新摘要到达 | 只接受更靠后的有效消息位置及其最新可见状态 | 最近消息摘要不倒退，撤回原文不继续泄露 |

接收重复请求时，如果第一次操作已经成功，即使用户之后被禁言或离群，也应在合法身份和原操作归属核对后返回原成功结果，不能把历史成功改写为失败。新的发送则按当前权限处理。

Redis 可执行的 Lua 操作用于连接路由中的原子比较与修改。Lua 是可以在 Redis 内执行简短操作组合的脚本语言。关键成员数量、消息去重和群主归属仍以 MySQL 的约束和事务为准，不用 Redis 中的一把锁替代持久化正确性。

## 七、登录、权限和附件访问

### 7.1 登录方案

1. 使用 Spring Security 管理身份和权限，采用可撤销的服务端登录记录。可撤销表示平台能够主动结束某个设备的使用资格。
2. MySQL 保存设备登录的有效状态和失效时间，Redis 保存便于查询的副本。最多3个设备的名额在数据库事务内控制。
3. 浏览器通过受保护的 Cookie 保存随机登录凭证。Cookie 是浏览器随访问携带的小段信息；该凭证不能直接包含密码，也不能仅凭用户公开编号推算。
4. 正式环境设置凭证不能由页面脚本读取，只通过加密连接发送，并限制来自无关站点的使用。
5. 普通访问采用 HTTPS，实时连接采用 WSS，分别是 HTTP 和 WebSocket 的加密传输方式。
6. 对改变业务数据的请求检查来源和操作资格，防止其他网站借用用户浏览器中的登录身份发起操作；实时连接建立时也检查来源。
7. 密码采用 Argon2id 进行单向校验。它是专门用于密码保护的计算方法，验证时比较计算结果，不保存或展示原密码；相关密码计算工具必须验证可在 JDK 17 上运行。
8. 缓存中的登录状态只能加速判断，不能绕过账号停用、密码修改和主动退出后的持久记录核对。

### 7.2 群历史与搜索权限

1. 保存每次加入和离开群组所对应的消息范围，作为历史消息、离线补拉、搜索和文件授权共同使用的依据。
2. 新成员不获得首次加入前的聊天；重新加入不获得离群期间的聊天。以前合法可见的历史按保存规则保留。
3. 第一版由 MySQL 完成限定会话与时间范围内的文字和文件名查询，并验证中文关键词效果。
4. 普通索引是帮助数据库定位部分数据的结构，不能认为有普通索引就能快速完成任意文字包含查询。搜索应限制范围、分页和调用频率，并单独测试。
5. 分页表示分批取得结果。历史分页使用会话位置继续读取，避免新消息到来时重复或跳过已有内容。

### 7.3 附件方案

1. OSS 使用不向公众开放的保存空间，由平台检查消息和访问者权限后提供访问。
2. 第一版附件下载经过平台受保护的下载入口，每次新请求检查消息状态、账号和历史可见范围，再读取 OSS 内容。不使用长期公开的文件地址。
3. 文件上传成功后，发送附件消息时重新检查发言权限。对象存在不代表消息已经成功，也不代表任意用户有权下载。
4. MySQL 保存附件与消息的对应关系，并区分临时文件、已关联文件和停止访问的文件。
5. 消息撤回或违规停止访问后，拒绝新的下载请求。已经下载完成的内容和已经开始传输的内容，不承诺能够从用户设备收回。
6. 临时文件超过24小时可以清理；正常附件按至少180天的业务期限保存，并协调举报材料的保留要求。

## 八、前端状态与恢复

1. Pinia 保存当前页面状态；IndexedDB 保存尚未确认结果的发送编号、必要内容和恢复位置。不能用页面刷新后就消失的状态承担恢复保证。
2. 用户主动发送时创建发送编号，自动重试继续使用原编号；主动重新发送相同文字才创建新编号。
3. 页面刷新后，先查询待确认发送的真实结果，再决定继续等待或提示用户操作，不自动将其作为新消息发送。
4. 消息显示结合唯一身份、会话位置和更新版本，处理重复、晚到、撤回及补拉交错。
5. 同一浏览器多个页面共用同一登录设备身份，页面间协调通知；多个页面不应造成设备名额重复占用或对同一消息反复提醒。
6. 设备连接可以包含多个页面连接，但设备登录状态只有一份。结束某个旧页面连接不等于结束整个设备登录。
7. 退出登录时结束该设备资格，并清理本地登录相关内容，避免另一个账号看到前一个账号的待确认消息。
8. 断网后逐步增加重连等待并加入随机间隔。随机间隔用于避免所有页面在相同时间同时重连。
9. 收到推送不等于已经阅读；只有符合需求中实际阅读条件时，才更新阅读位置。

## 九、测试与运行观测

### 9.1 正确性验证

JUnit 5 与 Testcontainers 用于自动验证数据库约束、事务和真实配套服务的交互。第一版至少覆盖《产品需求说明书》第十六章的24个场景，并重点检查：

1. 同一次发送重试1,000次只保存一条消息。
2. 100名成员各发送100条消息，完成恢复后结果完整且顺序一致。
3. 最后一个群名额、管理员名额和群主数量上限的同时竞争。
4. 发言与踢人、禁言、拉黑、停用、退出登录的交错。
5. 已读位置、撤回状态和最近摘要不被旧结果覆盖。
6. 本地事件已保存但尚未发送、事件已发送但确认丢失、分发安排已保存但消费确认丢失等时点发生重启。
7. RabbitMQ 不可用、Redis 副本失效、连接服务重启和单个接收者持续失败后的恢复。
8. 多段群成员期间的历史、搜索、补拉和附件可见范围一致。

### 9.2 处理能力与浏览器验证

JMeter 用于普通请求；Netty 测试工具用于长期连接和消息交互；Playwright 验证真实浏览器中的状态显示及多页面行为。

处理能力沿用需求中的目标：2,000名用户在线、分散会话每秒200次合法新发送、500人活跃群，以及离线1,000条消息的补齐。不同场景分别记录条件，不能将不同实验中的最佳数字拼成同一次结果。

所有压力测试结束后，必须核对接受和拒绝的操作、已保存消息、分发状态及接收结果。不只统计请求速度，也不以消息到达次数代替不同业务消息数量。

### 9.3 应观测的指标

1. 当前连接数、有效设备数、登录用户数和重连次数，分别统计，不相互代替。
2. 新发送数量、重复请求数量、明确拒绝数量和结果待确认数量。
3. 保存结果等待时间、接收显示等待时间和离线补齐耗时。
4. 本地待发送事件数量、最早等待时间、RabbitMQ 积压、异常事件数量。
5. 数据库锁等待、事务失败、死锁和有限重试数量。
6. 消息分发重试、设备确认超时、连接缓冲积压和丢弃的过期路由数量。
7. 权限拒绝、错误附件访问、群人数核对异常和数据修复结果。

运行记录使用操作、消息和事件的唯一身份关联处理过程；不记录明文密码、完整登录凭证或无必要的聊天原文。

## 十、部署与资源控制

### 10.1 环境安排

开发和测试使用 Docker Compose 组织服务。多个程序运行在同一台电脑上，可以验证交互与重启，但不能证明整台电脑故障后的可用性。

多节点验收至少运行两份连接服务和两份核心业务服务，以验证用户分布在不同服务实例时的聊天和故障恢复。RabbitMQ 的机器故障验证按第五章的独立机器要求进行。

MySQL 和 Redis 在本地可使用单实例。若正式部署仍为单实例，应如实记录其故障范围，不得把消息队列的多副本能力说成整个平台的高可用。高可用是指部分设备故障时仍能继续提供服务的能力。

### 10.2 连接处理与资源限制

1. Netty 的连接处理线程负责网络收发，不直接执行耗时数据库访问或等待其他服务。线程是程序执行工作的运行单元。
2. 耗时业务交给数量受控的工作线程和任务队列，不无限创建线程或积压任务。
3. 对每个连接的待发送内容设置上限。接收过慢时，暂停部分推送或结束连接，并允许随后补拉，不能无限占用内存。
4. 内部请求、数据库连接和文件下载均限制同时处理数量、等待时间及失败重试次数。
5. Redis 的短期故障不能绕过权限或导致用户路由永久错误；必要时暂时拒绝相关新操作，并允许随后恢复。
6. 服务退出前停止接受新工作，尽量完成已开始的操作；未完成工作保留可恢复身份，不能仅依赖程序退出前临时补救。

## 十一、第一版不额外引入的技术

| 技术类别 | 第一版处理决定与原因 |
| --- | --- |
| 第二套消息队列 | 只使用 RabbitMQ，避免两套机制重复承担同一职责 |
| 独立历史消息数据库 | 消息先使用 MySQL，满足第一版正确性和查询要求后，再按真实瓶颈评估 |
| 专用全文检索系统 | 第一版搜索限定会话和时间范围，先验证 MySQL 方案，不提前增加独立索引维护问题 |
| 分库分表中间件 | 分库分表是把数据拆到多个数据库或表中；第一版先保持必要的事务边界，不以预想规模提前拆分 |
| 跨服务事务框架 | 跨服务事务是协调多个服务共同完成数据变更；第一版将强关联操作保留在核心业务服务中，避免先增加协调复杂度 |
| 分布式锁作为核心正确性依据 | 分布式锁是让不同程序竞争同一操作资格的机制；本项目核心数据首先由 MySQL 的约束、锁和事务保护 |
| 复杂集群编排平台 | 第一版使用 Docker Compose；在真实部署规模需要时再评估更复杂的调度与管理工具 |
| 基于更高 JDK 的专属能力 | 统一以 JDK 17 为基线，不引入必须升级运行环境才能使用的功能 |

## 十二、开发顺序与技术验收

### 12.1 开发顺序

1. 固定 JDK 17 和兼容依赖，搭建三个服务及基础数据结构版本管理。

### 12.2 技术选型落实的验收边界

本文确定了技术方案，不代表项目程序已经搭建，也不代表版本启动验证、并发测试或处理能力目标已经完成。
