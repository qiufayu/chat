# 分布式即时通讯与群聊平台产品需求说明书

文档版本：1.0  
编写日期：2026年10月18日  
适用范围：项目第一版的设计、开发、测试与验收  
文档定位：描述使用者需要什么、业务如何运行、异常情况下应有什么结果，不指定开发工具和内部实现方法。

## 一、项目目标

### 1.1 项目定位

建设一个支持好友聊天和多人群聊的即时通讯平台。用户可以添加好友、创建群组、发送文字、图片和文件，在不同设备上查看消息，并在网络恢复后继续使用。

项目重点是在多人同时发送消息、同时管理群成员、同时更新阅读进度时，仍然保证业务数据正确，避免重复消息、消息顺序不一致、已读进度倒退和权限混乱。

“分布式”是指平台由多台计算机共同提供服务。对用户而言，无论自己和对方由哪台计算机提供服务，聊天规则和使用体验都应一致。

### 1.2 第一版应达到的业务结果

1. 用户能够完成注册、登录、添加好友、单独聊天和群聊。
2. 用户能够区分消息正在发送、平台已经保存、对方已经收到和对方已经阅读。
3. 网络中断、重复点击或自动重试不能导致同一次发送出现多条消息。
4. 同一群组中的成员最终应看到一致的消息顺序。
5. 用户更换设备或重新登录后，可以继续查看有权查看的历史消息。
6. 用户在多台设备上使用时，已读进度不能倒退，退出旧设备不能影响新设备。
7. 群成员数量、群主归属、禁言和成员权限在同时操作时仍然符合规则。
8. 平台能够通过明确的测试结果证明上述要求，而不以在线人数作为唯一评价依据。

## 二、使用角色与功能范围

### 2.1 使用角色

| 角色 | 可以执行的主要操作 | 主要限制 |
| --- | --- | --- |
| 未登录访客 | 注册、登录 | 不能查看聊天内容、群成员或其他用户的私人信息 |
| 普通用户 | 管理个人资料、好友、会话、消息和登录设备，申请加入群组 | 只能访问本人有权访问的数据 |
| 群成员 | 查看允许查看的群消息、发言、修改自己的群昵称、退出群组 | 受禁言、群容量和成员身份限制 |
| 群管理员 | 管理普通成员、处理入群申请、发布公告、执行禁言 | 不能移除群主或其他管理员，不能转让或解散群组 |
| 群主 | 管理群资料、管理员和成员，转让群主、解散群组 | 每个未解散的群组只能有一名群主 |
| 平台管理人员 | 处理举报、限制违规账号、处理违规群组、查看业务运行情况 | 不得无理由浏览用户私人聊天，不得冒充用户发言 |

群主和群管理员是用户在某个群中的身份，同一用户在不同群中可以拥有不同身份。

### 2.2 第一版包含的功能

账号与登录、好友申请与拉黑、好友单聊、群聊、文字消息、图片消息、文件消息、消息撤回、会话列表、未读提醒、消息搜索、离线恢复、多设备使用、群管理、举报处理和基础运行管理。

第一版提供电脑浏览器中的使用页面和管理页面。允许同一用户在不同设备的浏览器中登录，不要求提供独立的手机或电脑安装程序。

### 2.3 第一版不包含的功能

语音通话、视频通话、直播、红包、转账、支付、朋友圈、自动问答、消息自动翻译、外部通讯平台互通，以及超过第一版人数上限的超大群。

第一版不承诺在用户关闭全部使用页面后，仍能通过手机系统通知接收消息。此时用户再次登录，应能补齐消息和未读状态。

## 三、业务用语与默认规则

### 3.1 业务用语

| 用语 | 本文含义 |
| --- | --- |
| 会话 | 用户与一名好友的聊天，或用户参与的一个群聊 |
| 消息编号 | 平台为一条已保存消息分配的唯一标识，用于找到同一条消息；不代表其在会话中的先后位置 |
| 会话序号 | 一条消息在某个会话中的顺序位置，用于统一排序和恢复遗漏内容 |
| 同一次发送 | 用户发起的一次消息发送操作，包括因等待过久而进行的自动重试；重新输入相同文字并再次主动发送属于另一次发送 |
| 已保存 | 平台已经保存消息，后续即使当前页面关闭，也应能在规定的保存期限内再次查询 |
| 已送达 | 消息已经被接收者至少一个登录设备确认收到，不代表接收者已阅读 |
| 已读 | 接收者已经在打开的会话中阅读到对应位置；仅收到通知、打开会话列表或在后台接收消息不算已读 |
| 离线 | 用户当前没有能够正常接收消息的连接；离线不代表账号或历史消息被删除 |
| 多人同时操作 | 多个操作在相近时间内发生，处理过程可能互相交错，例如两个人同时申请最后一个群名额 |
| 登录设备 | 一次可独立管理的登录使用环境，例如一台电脑上的某个浏览器；同一浏览器中的多个页面按同一个登录设备管理 |
| 连接 | 使用页面与平台之间维持的联系，用于持续收发消息；网络中断后可能需要重新建立 |
| 平台管理人员 | 具有后台管理权限的工作人员，与普通群管理员不同 |

### 3.2 第一版默认业务限制

以下数值是本版需求的约定值，不代表已经完成的性能测试结果。后续如需调整，应更新本说明书并重新确认受影响的验收要求。

| 项目 | 第一版约定 |
| --- | --- |
| 同一账号同时登录的设备 | 最多3个 |
| 单个群组人数 | 最多500人，包含群主和管理员 |
| 单个群组管理员 | 最多5人，不包含群主 |
| 单个用户拥有的未解散群组 | 最多20个 |
| 单条文字消息长度 | 最多2,000个可见字符，换行和表情也计入限制 |
| 单张图片大小 | 最多20 MB；MB 是衡量文件大小的常用单位，同一单位下数值越大，文件越大 |
| 单个普通文件大小 | 最多100 MB，单位含义同上一项 |
| 消息撤回时间 | 从平台确认保存起2分钟内 |
| 好友申请有效期 | 7天 |
| 群邀请有效期 | 7天 |
| 入群申请有效期 | 7天 |
| 消息及其附件保存期限 | 自消息保存起至少180天；到期后的清理规则见第十二章 |
| 未完成发送的临时文件 | 超过24小时可以清理 |
| 登录最长持续时间 | 7天；到期后需要重新登录 |

## 四、账号、登录与个人资料

### 4.1 注册

1. 用户通过登录账号、密码和昵称进行注册。
2. 登录账号由6至20位英文字母或数字组成，英文字母不区分大小写，注册后不可自行修改。
3. 同一登录账号只能注册一次。多人同时注册相同账号时，只能有一人成功，其余人应收到明确提示。
4. 密码长度为8至32位，至少包含英文字母和数字，不允许全部为空格。设置密码时应告知规则。
5. 昵称为1至20个可见字符，可以重复；平台另外提供不可重复的用户编号，便于准确查找。
6. 注册失败不得留下能够正常使用的残缺账号，也不得占用一个实际上未注册成功的账号名。

### 4.2 登录与退出

1. 用户使用账号和密码登录。失败时统一提示账号或密码不正确，避免向陌生人确认某个账号是否存在。
2. 同一账号连续5次密码错误后，暂停该账号新的密码登录15分钟；已登录设备不因此自动退出。管理人员可处理恶意尝试引起的限制。
3. 达到3个登录设备后，新设备不得静默挤掉旧设备。用户验证身份后，可选择结束某个旧设备的登录再继续。
4. 用户能够查看当前登录设备的名称、最近活动时间和登录时间，并主动结束其他设备的登录。
5. 退出某个设备只结束该设备的使用资格，不清除聊天记录，不影响其他合法设备。
6. 修改密码后，除完成修改的当前设备外，其他设备应退出登录。
7. 登录到期或使用资格被取消后，页面应停止发送消息、获取新消息和下载受保护的附件，并提示重新登录。

### 4.3 账号恢复

1. 用户知道原密码时，可以自行修改密码。
2. 第一版不提供仅凭昵称、公开账号或用户编号完成的密码找回。
3. 忘记密码时，由平台管理人员按登记的身份核验流程处理。测试账号可以使用创建时登记的归属信息核验；无法核验时不得重置。
4. 管理人员不能查看原密码。重置后应要求用户在下次登录时修改密码，并结束原有登录。
5. 账号恢复操作必须记录处理人员、核验依据、时间和结果。未经补充真实身份核验方式，本版不承诺面向公众提供自助找回服务。

### 4.4 个人资料与账号状态

1. 用户能够修改昵称、头像和不超过200个可见字符的个人简介。
2. 修改资料不能改变用户编号、好友归属和历史消息的发送者归属。
3. 聊天页面中的当前头像和昵称可以随资料更新，但必须仍能识别实际发送账号。
4. 被停用的账号不得继续登录、发送消息、加入群组或修改资料。其他用户应看到适当提示。
5. 停用账号不等于删除该账号发送过的消息或解除其全部业务关系。

## 五、好友关系与单聊权限

### 5.1 查找用户与好友申请

1. 用户能够通过完整登录账号或用户编号准确查找其他用户，不提供全站用户列表。
2. 查找结果只展示建立联系所需的基本信息，不展示密码、登录设备和私人聊天内容。
3. 用户可发送好友申请，并填写不超过100个可见字符的说明。
4. 同一方向只能存在一条有效待处理申请，重复提交应返回原申请状态。
5. 对方可以同意或拒绝。申请过期后不能再直接同意，需要重新申请。
6. 双方同时发送申请时，不自动建立好友关系；任一有效申请被同意后，应只形成一份双方好友关系，并结束双方尚未完成的对应申请。
7. 申请处理后，其他设备再次处理应看到最终结果，不得反复改变关系。

### 5.2 好友维护

1. 好友可以互相发送单聊消息。用户不能向自己发送好友申请或单聊消息。
2. 用户能够设置仅本人可见的好友备注，备注不能改变对方账号资料。
3. 任一方删除好友后，双方好友关系解除，双方不得继续发送新的单聊消息。
4. 删除好友不删除双方各自有权查看的历史消息。
5. 重新成为好友后，应继续使用双方原有的单聊关系和历史顺序，不能形成两份互相独立的单聊。

### 5.3 拉黑

1. 用户可以拉黑其他用户。存在拉黑关系时，双方不能互发单聊消息或好友申请。
2. 拉黑不自动删除已经保存的历史消息，不自动解除好友关系；解除拉黑后，是否能聊天仍取决于好友关系是否存在。
3. 拉黑不改变共同群组的成员身份。双方在共同群中的消息仍按群规则显示。
4. 拉黑与发送同时发生时，应确定明确的业务先后：拉黑生效前已经接受的消息可以保留；拉黑生效后才处理的发送应被拒绝。
5. 被拒绝的消息不能在发送者重新登录后变成已成功发送。

## 六、会话列表与阅读状态

### 6.1 会话列表

1. 首次成功发送或接收消息后，应出现对应会话。用户也可以从好友或群组入口打开尚无消息的会话。
2. 同一对用户只对应一个单聊会话；同一个群组只对应一个群聊会话。
3. 会话列表展示名称、头像、最近一条可见消息的摘要、时间、未读提醒、置顶状态和免打扰状态。
4. 非置顶会话按最近消息的业务顺序排列。晚到的旧消息不能覆盖已经展示的新消息摘要。
5. 置顶只影响本人的排列，不影响其他用户。
6. 免打扰只影响提醒方式，不阻止消息保存、历史查询或未读状态更新。
7. 第一版不提供永久清空个人历史消息的功能，避免与离线恢复和多设备显示产生歧义。

### 6.2 未读与已读

1. 未读数量只统计用户有权查看、由其他人发送且尚未阅读的正常聊天消息。
2. 本人发送的消息、重复收到的同一条消息、入退群等提示、已经撤回的消息，不增加未读数量。
3. 未读超过99条时可以显示为99+，但实际阅读进度仍需准确保存。
4. 用户打开会话并实际阅读到某个位置后，可将该位置及以前的可见消息标记为已读。
5. 单聊应向发送者展示已送达和已读状态。已送达以对方至少一个设备确认为准，已读以对方任意设备的有效阅读确认为准。
6. 群聊第一版不展示每条消息的逐人成员已读名单，只维护每个用户自己的阅读位置。
7. 多设备的已读进度应合并到最靠后的有效位置，旧设备或延迟到达的阅读信息不能让进度倒退。
8. 未读状态允许短暂更新延迟，但恢复稳定后，各设备应一致，且不能出现负数。
9. 用户不能把阅读位置设置到尚不存在或无权查看的消息上。

## 七、消息发送、显示与撤回

### 7.1 消息类型

1. 第一版支持文字、单张图片、单个文件三类用户消息。
2. 每次发送一条消息；批量选择多个附件时，页面应明确每个附件分别形成一条消息，并分别展示结果。
3. 文字消息不能全部为空白，不得超过长度上限。超出限制时应在发送前提示，平台也必须拒绝不符合限制的提交。
4. 文件消息展示文件名、大小和下载操作。图片消息应能查看图片；无法预览时应说明原因。
5. 入群、退群、成员被移除、群主转让、群组解散和消息撤回等，以明显区别于普通发言的提示展示。

### 7.2 发送状态

| 状态 | 用户可理解的含义 | 后续行为 |
| --- | --- | --- |
| 正在发送 | 页面正在提交，尚未获得保存结果 | 可以等待，不应重复产生新的发送操作 |
| 结果待确认 | 网络中断或等待过久，暂时不知道平台是否已保存 | 先查询或重试原发送，不立即认定失败 |
| 已保存 | 平台已经保存这条消息 | 可以等待分发，并在历史消息中查询 |
| 已送达 | 单聊接收者至少一个设备已确认收到 | 不等于已读；群聊不展示逐人送达状态 |
| 已读 | 单聊接收者已阅读到这条消息 | 不应因较旧的通知而退回未读 |
| 发送失败 | 平台明确拒绝该发送，例如没有发言权限 | 显示原因；修正条件后可重新主动发送 |

1. 不得仅因页面暂时等待过久，就把已经保存的消息判为不存在。
2. 用户重新连接或重新打开页面后，应恢复此前结果待确认消息的真实结果。
3. 对同一次发送进行重试，只能得到同一条已保存消息，或者相同的明确拒绝结果。
4. 用户主动再次发送相同文字属于新消息，不能仅按文字相同判定重复。
5. 发送者其他登录设备也应收到该消息，但它们收到消息不算对方已送达。

### 7.3 消息顺序

1. 每个会话必须有唯一、明确的消息先后顺序。不同会话不要求共享同一个顺序。
2. 所有有权看到同一批消息的用户，最终应看到相同的相对顺序。
3. 顺序以平台确定的会话位置为准，不能以各用户设备显示的时间决定。
4. 两人几乎同时发言时，不承诺判断谁在现实中先按下发送键，但平台确定的先后关系不能因刷新或换设备而反复改变。
5. 已经展示的新消息之前若还有尚未取得的内容，页面应显示正在补齐，不得将缺失误认为历史已经完整。
6. 无权查看的内容、已过保存期限的内容和仅用于状态提示的位置，不应导致页面永久等待一条不存在的可见聊天消息。
7. 图片和文件以消息被平台接受的顺序排列，不以各接收设备下载完成的时间排序。

### 7.4 历史消息

1. 用户能够向前查看有权查看且仍在保存期限内的消息。
2. 查看历史期间收到新消息，不得导致原历史消息重复、遗漏或突然跳到其他位置。
3. 每次查看更多应说明是否还有历史，不要求一次加载全部内容。
4. 用户不能通过修改查询条件查看他人的单聊、未加入的群消息或无权访问期间的群消息。

### 7.5 消息撤回

1. 用户只能撤回自己发送且在2分钟内的消息。其他人不能冒充发送者执行撤回。
2. 第一版不赋予群主和群管理员撤回他人消息的能力；违规内容由平台管理人员按举报流程处理。
3. 撤回后，所有设备应显示撤回提示，普通用户不再能通过历史查询、搜索或附件下载查看原内容。
4. 撤回与阅读同时发生时，不能承诺接收者从未看见原内容；已经下载到用户设备的文件也无法从设备中收回。
5. 重复撤回应返回同一个撤回结果，不产生多个提示或恢复原消息。
6. 发送者退群、被移出群或删除好友后，仍可在原撤回时限内撤回自己原本有权发送的消息。
7. 撤回消息不能再次恢复为正常消息，其原始顺序位置保持可解释。

## 八、群组与群成员管理

### 8.1 建群与群资料

1. 用户能够创建群组，创建者自动成为群主，群组可以先只有群主一人。
2. 群名称为1至30个可见字符，群公告不超过1,000个可见字符。
3. 群主能够修改群名称、头像和公告；群管理员能够修改公告；普通成员只能修改自己的群昵称。
4. 群公告应展示更新人和更新时间。同一人连续提交相同操作不能产生重复公告提示。
5. 两名管理者同时修改同一项资料时，应保留一个明确的最终结果。较早打开的旧资料不能无提示覆盖已经生效的新资料，应要求重新确认。

### 8.2 加入群组

1. 群主和群管理员可以邀请自己的好友入群，受邀人明确同意后才加入，不得未经同意自动加入。
2. 用户也可以通过准确的群编号查看群名称和必要介绍，并提出入群申请。群主或群管理员同意后加入。
3. 非成员不能查看群成员完整名单和聊天记录。
4. 同一用户在同一群内只能有一份有效成员身份。重复同意、重复邀请和重复申请不得占用多个名额。
5. 群人数达到500人后，不得接受新的成员。多人竞争最后一个名额时，只能有一人加入成功。
6. 申请或邀请得到同意时，需要再次确认群未解散、名额充足、账号可用且处理人仍有权限。
7. 已被移出群的用户可以重新申请，但必须重新获得同意，之前的已处理申请不能再次用于入群。

### 8.3 管理员和群主

1. 只有群主可以设置或取消管理员，管理员不能设置其他管理员。
2. 管理员最多5人，同时设置时也不能突破上限。
3. 群主可移除任何其他成员；管理员只能移除普通成员。
4. 群主转让时，接任者必须是当前有效成员、账号正常，且接任后拥有的未解散群组不能超过20个。不同群同时转让给同一人时，也不能突破该限制。
5. 转让成功后，原群主成为普通成员，新群主拥有群主权限。如新群主原为管理员，其管理员名额应释放。
6. 无论多少次转让同时发生，一个未解散群都必须始终只有一名有效群主。
7. 转让与接任者退出、被移除同时发生时，应只接受符合最终业务顺序的操作，不得出现群主已不在群中的结果。

### 8.4 禁言

1. 群主可以禁言其他成员；管理员只能禁言普通成员，不能禁言群主或其他管理员。
2. 支持解除禁言、禁言10分钟、1小时、24小时，以及持续禁言直到被解除。
3. 群主可以开启全员禁言。开启后，只有群主和管理员可以发送消息。
4. 被禁言成员仍可阅读自己有权查看的群消息。
5. 发言与禁言同时发生时，以平台确定的生效先后为准：禁言生效前接受的消息保留，生效后才处理的发送拒绝。
6. 禁言期间拒绝的发送，不能在禁言结束后自动变成一条新消息；用户需要主动重新发送。
7. 成员成为群主或管理员时，原来针对其普通成员身份设置的单独禁言应解除，避免新身份与旧限制冲突。

### 8.5 退出、移出与解散

1. 普通成员和管理员可以主动退出。群主必须先转让群主，或者解散群组，不能直接退出留下无群主的群。
2. 退出或移出群组生效后，该用户不能发送新群消息，也不能查看生效后的新群消息。
3. 退出或被移出前已经有权查看的历史，在保存期限内仍可只读查看，但不再获得当前成员名单和后续群资料更新。
4. 用户重新加入后，可查看之前有权查看的内容和本次加入后的内容，不得查看离群期间的消息。
5. 新成员不能查看首次加入前的聊天历史，可以查看当前群公告。
6. 群主解散群组需要明确确认。解散后不能发言、入群或继续修改群资料，所有原成员获得解散提示。
7. 解散前已经被接受的消息保留；解散后才处理的发送必须拒绝。历史内容按原有权限和保存期限继续可查。
8. 解散与入群、转让、发言同时发生时，结果必须能按明确的先后关系解释，不能出现已经解散又重新可用的群。

## 九、离线恢复与多设备使用

### 9.1 离线消息

1. 接收者离线不应阻止合法消息被接受和保存。
2. 用户再次登录或网络恢复后，应补齐保存期限内、有权查看而尚未取得的消息。
3. 恢复期间也应接收新消息，补回的旧消息与实时到达的新消息应去除重复并按会话顺序显示。
4. 只完成连接恢复不能被当作消息已补齐；补齐未完成时，应有明确提示。
5. 离线时间超过保存期限时，应告知哪些历史范围已不可获取，不能伪装成用户从未收到过消息。
6. 离线期间已退出或被移出群组的用户，只能补齐成员资格有效期间允许查看的内容。

### 9.2 多设备一致性

1. 用户在一个设备发送的消息，应出现在其他已登录设备的同一会话中。
2. 置顶、免打扰、好友关系、拉黑状态和有效阅读进度应在多设备间保持一致。
3. 另一个设备晚到的旧消息或旧状态不得覆盖更新的会话摘要和阅读进度。
4. 一个旧连接断开时，不得错误结束该设备已经重新建立的新连接，也不能移除其他设备的有效连接。
5. 用户主动结束某设备登录后，该设备不能继续取得受保护的新消息；此前已经下载到设备的内容不在远程删除承诺之内。
6. 同一设备打开多个页面时，不应因此产生多份消息、重复通知或互相踢出登录。

### 9.3 网络异常提示

1. 页面应区分正常连接、正在恢复、需要重新登录和服务暂时不可用。
2. 不稳定网络下应自动尝试恢复，恢复期间保留尚未确认发送结果的内容。
3. 用户明确退出登录后，不应继续自动登录或继续使用原账号发送消息。
4. 服务恢复后，应先核对不确定的发送结果，再允许用户决定是否作为新消息重新发送。

## 十、图片与文件

1. 用户选择附件后，应先检查大小和允许的文件类型，不符合规则时清楚提示。
2. 第一版图片支持常见照片格式，包括通常以 jpg、jpeg、png、webp 结尾的图片文件；平台还应检查实际内容，不能只相信文件名。
3. 普通文件支持文档、表格、演示文稿、纯文字和压缩文件等常用类型；禁止直接分享可执行程序和脚本文件，即能够被设备当作程序运行的文件。
4. 文件类型允许范围应由平台统一公布。更改范围后，只影响之后的新上传；对已有违规文件可按审核规则停止访问。
5. 文件上传成功并不代表消息发送成功。只有附件已可用且发送者有发言权限时，才能形成已保存的附件消息。
6. 上传成功后若用户已被禁言、移出群或失去好友聊天权限，发送应被拒绝，不得因文件已经上传而绕过权限。
7. 上传中断或失败时，应保留清楚的失败状态，允许重新尝试；不能向接收者展示无法取得的成功文件消息。
8. 同一次文件消息的重试不得生成多条消息。允许因重新上传产生临时文件，但不应长期占用空间。
9. 文件只能由有权查看对应消息的用户访问。仅知道一个下载地址，不能获得访问资格。
10. 消息被撤回、违规内容被停止访问，或访问者失去相应历史查看权后，不得继续获得新的受保护下载。
11. 文件名应保留可识别的原始名称；遇到重名文件，不能覆盖其他消息的文件。
12. 临时文件超过24小时可以清理。已形成正常消息的附件，在消息保存期限内应保持可用。

## 十一、搜索与通知

### 11.1 搜索

1. 用户可在一个会话内按关键词和时间范围查找文字消息，也可按文件名查找附件消息。
2. 第一版不要求搜索图片中的文字或文件内部正文。
3. 搜索只能返回当前用户有权查看且仍在保存期限内的内容。
4. 已撤回、因违规停止普通用户访问的内容不应在搜索结果中显示原文或可访问的原附件。
5. 搜索结果应显示所在会话、发送人、时间和必要摘要，并允许定位到对应历史位置。
6. 搜索与会话历史对同一消息的可见性必须一致，不能在历史中无权查看，却能从搜索中获得内容。

### 11.2 通知

1. 页面保持打开且用户已登录时，应提供新消息和业务处理结果提醒。
2. 需要提醒的业务包括好友申请及结果、群邀请、入群申请结果、被移出群、群解散和账号受限。
3. 同一个业务结果重复到达时，不应产生多条相同通知。
4. 免打扰会话不弹出声音或浮层提醒，但继续保留会话内消息和未读标识。
5. 默认提醒只显示发送者和消息类型，用户主动开启内容预览后才可显示消息摘要，避免在公共屏幕暴露私人内容。
6. 正在打开并阅读当前会话时，不应对同一条消息反复发出打扰性提醒。

## 十二、平台管理、隐私与数据保存

### 12.1 举报处理

1. 用户可举报有权查看的消息、用户或群组，填写原因，并选择必要的关联消息。
2. 举报提交后提供处理状态，包括待处理、处理中和已完成。
3. 管理人员处理举报时，只能访问处理该举报所必需的信息，不提供无条件浏览所有私人会话的入口。
4. 用户撤回消息不自动取消已经提交的举报。举报提交时应保留必要的投诉依据，普通用户不能通过举报重新查看已经撤回的原内容。
5. 处理结果可包括不采取措施、警告、限制发言、停用账号、关闭群组和停止违规内容访问。
6. 每次处理记录举报对象、处理人员、原因、时间、措施及有效期。
7. 被处理用户应能看到与本人相关的处理原因、持续时间和申诉入口；申诉由有权管理人员处理，不要求第一版自动裁定。

### 12.2 平台管理与权限

1. 管理页面应与普通用户页面分开授权。普通群主不能因此访问平台管理页面。
2. 管理人员可查看账号和群组状态、举报数量、异常业务数量和服务使用情况。
3. 停用账号、关闭群组、重置密码、访问举报材料和导出相关处理记录等敏感操作应留存操作记录。
4. 管理人员不能修改消息的原发送人和原发送内容，也不能把未读直接改为用户已读。
5. 操作记录至少保存180天，普通用户无权修改或删除；处理人员也不能通过普通管理功能抹除自己的操作记录。

### 12.3 数据保存与清理

1. 正常消息和附件自消息保存起至少保留180天，平台应向用户说明该期限。
2. 达到180天后允许按统一规则清理，但应保留清楚的历史可获取范围，不得让用户误以为仍可查看已清理内容。
3. 已经进入投诉处理的必要材料，至少保存至案件结束后30天。若超过普通历史保存期限，仅用于授权处理，不恢复普通用户的历史访问。
4. 用户退出、删除好友、离群、被停用和群解散，不自动触发全部历史删除。
5. 第一版不提供用户自行注销账号和主动清除所有个人数据的功能。若后续开放公众服务，应另外确认相关处理要求和流程。
6. 临时文件清理、历史清理和投诉材料保留之间应明确区分，不能因临时清理误删正常消息附件。

### 12.4 故障恢复与隐私边界

1. 部分功能暂时中断、页面异常、提供服务的程序重新启动或短暂网络故障后，已经确认保存的消息和有效业务关系应可恢复。
2. 至少每日保留一份可用于恢复的完整数据副本，并保留最近7天的副本；数据副本是用于损坏后恢复的额外保存内容。
3. 应实际验证恢复结果，包括消息、群成员、好友关系和阅读进度，而不只确认副本文件存在。
4. 对全部正在使用的数据保存设备同时毁损等严重事故，第一版以最近一次可用副本作为恢复依据，可能缺少最近一次额外保存之后的数据，按本版每日保存一次的要求，该范围最多为24小时；这类事故不得与日常故障恢复能力混为一谈，恢复后应说明受影响范围。
5. 页面和普通运行记录不得明文显示用户密码或不必要的私人消息内容。
6. 第一版不承诺只有聊天双方能够解读消息内容的特殊保密能力，但必须执行访问授权，不允许陌生用户或无权管理人员随意读取。

## 十三、多人同时操作时的数据正确性要求

本章是项目的核心验收依据。即使出现延迟、重复提交、网络中断或服务重新启动，最终结果仍必须符合以下规则。

### 13.1 消息唯一与结果可追溯

1. 同一次发送，无论重试多少次，只能形成一条业务消息和一个确定的结果。
2. 每条已保存消息应能关联到发送者、会话和原发送操作，便于确认重复提交是否指向同一条消息。
3. 结果待确认不是另一次发送，平台和页面不能因为等待过久自动创建新的业务消息。
4. 重复分发不能造成消息重复显示、未读重复增加或通知重复出现。

### 13.2 顺序与状态一致

1. 同一会话中已确定的消息先后关系不能改变，同一位置不能属于两条不同的正常消息。
2. 会话摘要不能被晚到旧消息覆盖。
3. 已读位置只能前进；已送达和已读不能因旧状态到达而被撤销。
4. 消息被撤回后，晚到的原消息不能让原内容重新出现。
5. 不要求所有设备在同一瞬间完成更新，但在完成恢复与补齐后，应得到一致结果。

### 13.3 成员、名额与身份一致

1. 同一用户不能在一个群里出现多份有效成员身份。
2. 群人数始终等于有效成员人数，不能为负，也不能超过500人。
3. 管理员不能超过5人，群主转让不得导致零名或多名群主。
4. 入群申请只允许一个最终处理结果，不能同时显示已同意和已拒绝。
5. 退出、移出、解散、禁言与发送交错时，必须按照一个明确的业务生效先后决定权限，不能由不同页面各自判定。
6. 对于同时发生但结果分别为成功和失败的操作，应分别给出结果，不能为保持表面成功而留下错误成员数或多余身份。

### 13.4 登录与权限一致

1. 旧连接关闭不得取消已经生效的新连接。
2. 主动取消设备登录后，旧请求不能恢复该设备的使用资格。
3. 发送、历史查询、搜索和附件访问应遵循一致的权限范围。
4. 所有成功操作必须符合其生效时的账号、好友和群成员状态。

### 13.5 被接受的消息与后续处理一致

1. 平台确认保存的消息，在规定的保存和访问范围内必须可查询，不能只有成功提示而没有历史记录。
2. 后续分发暂时失败时，应可继续尝试；不能因为一次推送失败就删除正常消息或伪造已送达。
3. 用户始终离线、失去权限、超过保存期限等情况，应按对应业务规则处理，不把“最终送达”解释为无条件强制送达。
4. 异常处理完成后，应能分清哪些消息已保存、哪些被拒绝、哪些仍待处理，不得长期存在无法解释的中间结果。

## 十四、体验、处理能力与异常要求

### 14.1 体验要求

1. 发送中、恢复中、无权限和服务不可用必须有用户可理解的提示，不向普通用户展示内部错误细节。
2. 出现异常时，优先保留用户已输入内容和不确定的发送结果，避免无提示清空。
3. 普通操作应支持鼠标和键盘使用，核心状态不能只靠颜色区分。
4. 时间统一按平台确认的时间解释，页面可以按用户所在时区显示，但不能因此改变消息顺序或撤回时限。
5. 身份、群资料和未读数存在短暂更新延迟时，不得因此允许越权发言或下载。

### 14.2 第一版处理能力目标

以下是计划验证的测试目标，不是已经达到的成果，也不是要求必须使用某种设备。验收报告必须注明计算机配置、参与提供服务的计算机数量、网络条件和测试持续时间。

| 场景 | 第一版验收目标 |
| --- | --- |
| 同时在线 | 2,000个不同用户持续在线30分钟，期间能够收发消息 |
| 持续文字发送 | 每秒提交200次合法的新文字发送，持续10分钟，发送分布在至少100个会话中 |
| 发送结果等待 | 在上述持续发送场景下，至少99%的合法发送在2秒内获得明确保存结果；没有获得结果的操作必须可恢复确认 |
| 在线单聊显示 | 接收者网络正常且设备在线时，至少99%的消息在发送请求提交后3秒内显示 |
| 活跃群聊 | 一个500人群中所有成员在线，群内合计每秒发送10条文字消息，持续5分钟；至少99%的有效接收在5秒内显示 |
| 短时断线恢复 | 用户离线期间产生1,000条有权查看的文字消息，网络恢复后，至少99%的被测设备在30秒内补齐；无法完成时显示真实进度 |
| 正确性底线 | 全部测试结束并完成恢复后，没有无法解释的已保存消息缺失、重复业务消息、错误权限、人数超限或已读倒退 |

上述目标应分场景验证，不默认要求所有最高负载同时发生。额外增加的负载组合应单独说明，不能将不同场景的最好结果拼成一次测试结果。

“至少99%”指每100次符合条件的被测操作中，至少99次满足规定时间，其余操作仍必须有明确结果，不能因此被允许丢失或越权。

### 14.3 超出处理能力时的行为

1. 资源不足时可以限制新登录、新发送或大批量历史读取，但应告知用户稍后再试。
2. 限制措施不得把明确拒绝的消息显示为已保存，也不得为提高速度跳过成员和权限检查。
3. 单个用户持续异常发送时，应限制该用户，而不是无差别使所有会话不可用。
4. 一个群特别活跃时，不应无限占用处理资源导致所有其他群都无法工作。
5. 大量用户同时恢复连接时，应逐步恢复服务，避免持续反复断开，并保留正确的消息恢复位置。

## 十五、主要使用流程及异常结果

### 15.1 单聊发送

1. 用户登录后进入好友会话，输入文字，然后发送。
2. 平台确认账号、好友关系、拉黑状态和文字内容有效。
3. 接受后显示已保存，接收者在线时继续显示送达和阅读结果。
4. 接收者离线时保留消息，待其重新登录补齐。
5. 发送途中断网时显示结果待确认；恢复后仍对应原发送，不自动多发一条。

### 15.2 群聊发送

1. 成员进入群聊，发送消息。
2. 平台确认群未解散、成员身份有效且未被限制发言。
3. 接受消息并确定会话顺序，向有权查看的在线成员提供消息。
4. 部分成员暂时离线或接收缓慢，不影响已经接受的消息保留。
5. 发送与禁言、移出或解散同时发生时，按照业务生效顺序给出唯一结果。

### 15.3 入群

1. 用户收到邀请或主动提出入群申请。
2. 完成所需同意后，确认群状态、人数、账号状态和处理权限。
3. 成功则只增加一份成员身份和一个名额，并告知申请人。
4. 人数已满、申请失效或权限变化时明确拒绝，不占用名额。
5. 同一结果在多个页面查看或重复处理，不改变最终状态。

### 15.4 更换设备和恢复网络

1. 用户在允许的设备数量内登录，取得本人有效会话。
2. 补齐有权查看的消息、阅读进度和会话设置。
3. 同时接收新内容，对重复内容只展示一次，历史与新内容按统一顺序排列。
4. 对原设备尚未确认的发送，恢复真实结果。
5. 登录已失效时要求重新登录，不在旧身份下继续操作。

### 15.5 违规处理

1. 用户选择有权查看的内容并举报。
2. 平台保存必要依据，由有权限的管理人员处理。
3. 处理结果通知相关用户，适用限制立即影响后续操作。
4. 对举报结果有异议时可申诉，原处理记录不得因此消失。

## 十六、验收场景与判定标准

验收应同时检查页面显示、再次登录后的查询结果、受影响用户的实际权限，以及管理人员可核对的业务记录。不能仅凭某一页面暂时显示正常认定通过。

| 编号 | 验收场景 | 必须满足的结果 |
| --- | --- | --- |
| 1 | 多人同时注册同一个账号 | 只有一个账号创建成功，其他人得到明确提示，无残缺账号 |
| 2 | 两名用户相互申请好友，并在多个设备上同时同意 | 只形成一份双方好友关系，不重复增加好友或通知 |
| 3 | 同一次发送同时重试1,000次 | 只形成一条业务消息，其他设备和接收者也只展示一条 |
| 4 | 用户主动发送两次相同文字 | 正确形成两条消息，不误判为一次发送 |
| 5 | 消息已保存，但发送者未收到保存结果就断网 | 恢复后找到原消息，不能再多出一条，也不能一直显示失败 |
| 6 | 100名成员同时向同一群发送，每人发送100条不同消息 | 10,000次合法发送各有一个结果；全部已保存消息在各有权设备中顺序一致、无重复 |
| 7 | 恢复历史消息的同时持续接收新消息 | 补齐后不重复、不遗漏，旧消息不能覆盖新摘要 |
| 8 | 多设备以随机顺序上报不同阅读位置 | 最终位置等于最大的合法阅读位置，不能倒退或超过可见范围 |
| 9 | 499人群中，两名不同用户同时完成入群条件 | 只能有一人成功，最终人数为500人，另一人明确得知失败 |
| 10 | 同一入群申请被两名管理员同时同意或分别同意与拒绝 | 只有一个最终结果，人数和成员身份与结果一致 |
| 11 | 两次群主转让同时进行 | 最终只有一名群主，原群主和其他成员身份可解释 |
| 12 | 发言与禁言、移出或群解散同时发生 | 按明确生效先后接受或拒绝，不出现操作生效后仍无条件发言 |
| 13 | 用户退出后产生新群消息，再重新入群 | 可见范围符合两段成员期间，不能看到离群期间消息 |
| 14 | 旧连接延迟断开，新连接已建立 | 新连接仍能正常收发，其他设备不受影响 |
| 15 | 用户主动结束一个旧设备登录 | 旧设备不能继续取得新消息或受保护附件，新设备正常使用 |
| 16 | 消息已保存后，暂停后续分发，再恢复 | 已保存消息仍可查询，恢复后继续处理；重复处理不多显示或重复计数 |
| 17 | 消息撤回后，某设备才收到原消息 | 最终显示撤回提示，原内容不会重新出现 |
| 18 | 猜测他人消息、群组或附件的访问位置 | 不泄露无权查看的内容，搜索也不能绕过权限 |
| 19 | 上传文件成功后，发送者被禁言或移出群，再提交发送 | 发送被拒绝，不出现已保存附件消息，临时文件按规则清理 |
| 20 | 阅读、撤回和重复消息交错发生 | 未读不为负、不重复增加，已读不倒退，撤回结果稳定 |
| 21 | 同一会话的旧摘要晚于新摘要到达 | 最终保留更新的摘要和排列位置 |
| 22 | 发送量超过处理能力 | 可明确拒绝或延迟，不能伪造保存成功、跳过权限或形成错误数据 |
| 23 | 从规定的数据副本恢复一套测试数据 | 消息、好友、群成员和阅读进度可核对；明确记录恢复范围和可能缺口 |
| 24 | 在保留期边界查询历史、搜索和下载附件 | 三者遵守一致权限和保存规则，并说明不可获取的历史范围 |

对于同时操作的测试，应保留操作发生时间、参与账号、实际成功与失败结果，以及最终业务状态。若业务规则允许不同先后顺序产生不同合法结果，不要求每次由同一个参与者成功，但要求每次结果都符合本说明书。

本章中的测试还应覆盖群主拥有群组数量的上限、管理员数量上限、账号被停用后的权限，以及搜索和附件访问中的同类情况，判定规则与正文保持一致。

## 十七、交付范围与完成标准

### 17.1 应交付的业务成果

1. 可供用户实际使用的聊天页面，覆盖本说明书第一版功能。
2. 可供授权人员使用的管理页面，覆盖举报、账号和群组处理。
3. 用于演示单聊、群聊、多设备、退出重进和违规处理的测试账号与操作说明。
4. 覆盖第十六章场景的测试记录，包含正确结果与异常结果。
5. 处理能力测试报告，注明测试条件、持续时间、成功与失败数量、等待时间和恢复结果。
6. 数据保存、临时文件清理、故障恢复和账号恢复的使用说明。
7. 已知限制清单，说明尚未达到的目标及其对用户的影响，不将未完成内容描述为已支持。

### 17.2 第一版完成标准

1. 范围内功能均可实际使用，未完成项不能仅以页面占位代替。
2. 重复消息、消息缺失、无权访问、群人数超限、多名群主、已读倒退和旧连接误伤新连接等核心问题均已通过验收。
3. 对不确定的发送结果和异常业务有明确恢复路径，不长期依赖人工猜测。
4. 处理能力目标有实际测试证据；未达到的目标如需调整，必须更新需求和验收结论，不能修改统计口径掩盖问题。
5. 使用者能够根据状态提示理解发生了什么、哪些操作成功、哪些需要重试，以及何时需要重新登录。

本项目的最终评价重点是：在多人同时操作和发生常见故障时，业务结果仍然正确、权限仍然有效、历史仍然可核对，而不仅是能够维持多少在线连接。
