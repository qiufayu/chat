## 部署与兼容

已有数据库先在 `user_server` 执行 `database/migrations/20261124_friend_request.sql`，再更新用户服务和连接服务。MySQL 客户端示例：

```sql

SOURCE E:/Project/five/database/migrations/20261124_friend_request.sql;
```

新环境使用 `database/database.sql`，其中已经包含申请表。增量脚本只创建新表，保留已有好友、备注、会话和消息数据，不自动执行。

正常账号状态统一为 `users.status=1`；`0` 表示异常，`2` 表示封禁。旧版注册与登录错误地使用了 `0` 作为正常状态，现已修正。升级前检查旧账号状态，只对确认正常的指定账号修正为 `1`，不要批量解除异常或封禁状态。例如先核查：

```sql
SELECT id, account, status FROM users WHERE status <> 1;
-- 确认具体账号确实正常后，再按其实际 id 修正：UPDATE users SET status = 1 WHERE id = ...;
```

`POST /friend/apply` 从“立即成为好友”改成返回申请对象，需要对方同意。原生测试页面 `temo/front_text_of_single` 中旧的立即成为好友交互尚未接入申请审批；调用方应按下面接口更新。

## 接口

全部需要登录。请求头使用 `authorization: <原始 accessToken>`、`device-id: <设备ID>`；JSON 请求指定 `Content-Type: application/json` 和 `Accept: application/json`。`user-info` 由网关注入，外部调用方不能自行指定身份。

| 方法与路径 | 参数 | 返回 |
| --- | --- | --- |
| `GET /friend/search` | `account` 或 `userId`，二选一，精确匹配 | 对方公开资料 |
| `POST /friend/apply` | `{"account":"对方账号","message":"申请说明"}`；也可用 `friendId` 替代 `account` | 申请对象 |
| `GET /friend/requests` | `direction=incoming`（默认）或 `outgoing`；`beforeId` 可选；`limit` 默认50 | 当前用户收到或发出的申请 |
| `POST /friend/requests/{requestId}/accept` | 路径中的申请ID，无请求体 | 申请最终状态 |
| `POST /friend/requests/{requestId}/reject` | 路径中的申请ID，无请求体 | 申请最终状态 |
| `GET /friend/list` | `afterId=0`（默认）；`limit` 默认50 | 当前双向好友列表 |
| `POST /friend/verify` | `{"toId":2}`；兼容可选的 `senderId`，必须等于登录用户 | 是否允许单聊：`true` / `false` |
| `DELETE /friend/{friendId}` | 对方用户ID，无请求体 | HTTP 204 |

`limit` 范围1～100。申请按ID倒序分页，将上一页最后一条的 `id` 作为下一页 `beforeId`；好友按对方ID升序分页，将最后一条 `friendId` 作为下一页 `afterId`。只查询当前用户可见的数据，不提供全站用户列表。

申请对象包含 `id`、`applicantId`、`receiverId`、双方账号/昵称、`message`、`status`、`createdAt`、`expiresAt`、`handledAt`。好友/搜索资料仅包含 `friendId`、`account`、`nickname`、`avatar` 和可选的本人备注 `remark`，不返回密码、手机号或登录信息。

## 操作流程与状态

1. A 按账号或用户ID查找 B，提交申请；此时校验好友返回 `false`。
2. B 查询 `incoming`，用申请 `id` 同意；只有 B 可以处理此申请，不能通过请求体冒充 B。
3. 同意后在一个事务中创建或恢复双方好友关系，并完成双方尚未结束的对应申请。A、B 均可校验并发送单聊。
4. 任一方删除好友，事务内将双方关系标记为删除，并取消双方待处理申请。此后双向校验为 `false`；不删除历史消息和会话。
5. 重新添加必须提交新申请并重新同意。恢复原有好友记录、备注和单聊会话，不重复创建历史会话。

状态如下：

| 状态 | 含义 |
| --- | --- |
| `PENDING` | 等待接收方处理，有效期7天 |
| `ACCEPTED` | 已同意 |
| `REJECTED` | 已拒绝 |
| `EXPIRED` | 已过期，不能继续同意 |
| `CANCELLED` | 删除关系时取消了未完成的申请 |

同方向有效待处理申请重复提交返回同一申请ID；双方交叉申请不自动同意。拒绝、过期、取消后重新申请生成新ID，并保留旧记录。过期状态在查询时计算，在重新申请或处理时落库。

同意/拒绝的重试返回已有终态，不反复改变关系；删除后重复同意旧的 `ACCEPTED` 申请只返回历史结果，不恢复好友。判断当前能否聊天请调用 `/friend/verify`。删除可重复调用。

禁止给自己申请、给不存在或不可用的账号申请；存在任一方向拉黑记录时禁止申请或同意，也不能发送单聊。申请说明最多100字符。

## 一致性与消息权限

所有好友变更在数据库事务内，按用户ID从小到大锁住双方用户行，再检查申请和更新关系。固定顺序避免交叉申请/同意/删除采用不同锁顺序。读取使用 READ COMMITTED，等待锁后看到其他操作已提交的状态；好友表仍由 `(user_id, friend_id)` 唯一索引保证方向记录唯一。

发送消息时，连接服务显式携带连接绑定的用户身份，通过用户服务核对双方数据库关系、双方账号状态和拉黑状态。客户端传入的 `senderId` 不能替代连接身份。数据库校验通过是本次发送的权限判定点；并发删除之前已经通过判定的在途消息可以继续处理，删除提交之后才执行的校验会失败。已经保存的 Outbox 和历史消息不因删除而丢弃。

旧 Redis 好友集合不再作为发送权限依据；同意和删除提交后会尝试清理双方旧缓存。缓存缺失、残留、清理失败均不能绕过数据库校验。用户服务不可用时拒绝新发送。每条新聊天校验会增加一次内部 HTTP 请求，旧压测结果不能直接代表变更后的吞吐。

公共 HTTP 异常处理放在 `chat-common` 的 `GlobalExceptionHandler`，由 MVC 自动配置注册；非 MVC 服务不加载该配置。业务错误统一返回 `{"code":403,"message":"..."}`，HTTP 状态与错误码一致。常见错误：400参数错误，401未登录，403无权处理/账号不可用/拉黑，404用户或申请不存在，409已经是好友。
